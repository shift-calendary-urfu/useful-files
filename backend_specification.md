# Спецификация Backend — «Календарь смен»

Основной сценарий:

> Собственник создаёт бизнес и точку → добавляет сотрудников → назначает смены → сотрудник входит и просматривает своё расписание.

## 1. Модели БД

### Обозначения

- `UUID` — идентификатор.
- `string` — строка.
- `int` — целое число.
- `datetime` — дата и время.
- `enum` — значение из списка.
- `JSON` — структурированные данные.
- `?` — необязательное поле.
- `FK` — ссылка на другую модель.

Все поля обязательные, кроме помеченных `?`. Системные поля заполняет сервер.

У основных моделей есть общие поля:

- `id: UUID`
- `created_at: datetime`
- `updated_at: datetime`

У таблиц связи используется составной ключ из двух идентификаторов.

### Основные модели

| Модель | Назначение | Поля сверх общих |
|---|---|---|
| User | Аккаунт пользователя | `provider: string`, `provider_user_id: string`, `display_name: string`, `email: string?`, `phone: string?` |
| Business | Бизнес | `name: string`, `timezone: string` |
| Membership | Участие пользователя в бизнесе | `user_id: UUID FK User`, `business_id: UUID FK Business`, `role: enum(owner, admin, employee)` |
| Workplace | Рабочая точка | `business_id: UUID FK Business`, `name: string`, `timezone: string`, `address: string?`, `phone: string?`, `description: string?` |
| Employee | Запись сотрудника | `business_id: UUID FK Business`, `membership_id: UUID FK Membership?`, `full_name: string`, `email: string?`, `phone: string?` |
| EmployeeWorkplace | Связь сотрудника с точками | `employee_id: UUID FK Employee`, `workplace_id: UUID FK Workplace` |
| Shift | Плановая смена | `business_id: UUID FK Business`, `workplace_id: UUID FK Workplace`, `employee_id: UUID FK Employee`, `starts_at: datetime`, `ends_at: datetime`, `comment: string?` |

`timezone` — IANA-пояс, например `Asia/Yekaterinburg`.

### Связи и ограничения

- User связан с Business через Membership.
- У пользователя одна роль в конкретном бизнесе.
- Структура «собственник → бизнес → точки» требует согласования с куратором. Текущая модель — рабочая гипотеза.
- Business содержит точки, сотрудников и смены.
- Employee связан с несколькими Workplace через EmployeeWorkplace.
- Сотрудник может существовать в справочнике без аккаунта.
- Аккаунт связывается максимум с одной записью сотрудника в каждом бизнесе.
- Точка, сотрудник и смена относятся к одному бизнесу.
- Повторяющиеся пары в таблицах связи запрещены.
- Пара `provider + provider_user_id` уникальна.
- Создание бизнеса и участия собственника выполняется одной транзакцией.
- Назначение сотрудника на точку не выдаёт административные права.
- Отдельная модель календаря не нужна: календарь формируется из смен.

## 2. Эндпоинты API

Тела запросов передаются в JSON. Текущий пользователь определяется по сессии.

Для рабочих объектов используется префикс:

`/api/businesses/:business_id`

Например:

`GET /api/businesses/:business_id/workplaces`

В таблице рабочих операций пути указаны относительно этого префикса.

### Авторизация и бизнес
| METHOD + URL | Назначение | Принимает | Возвращает |
|---|---|---|---|
| `GET /api/auth/yandex/start` | Начать вход через Яндекс ID | `return_to?` — разрешённый адрес возврата | Перенаправление на авторизацию |
| `GET /api/auth/yandex/callback` | Завершить авторизацию | `code`, `state` либо ошибка провайдера | Создание / поиск пользователя, открытие сессии, перенаправление во frontend |
| `GET /api/session` | Получить аккаунт и доступ | Cookie сессии | Пользователь, бизнесы, роли, права, `employee_id`, доступные точки, серверное время |
| `POST /api/auth/logout` | Выйти из аккаунта | Текущая сессия | `204`, сессия завершена |
| `POST /api/businesses` | Создать бизнес | `name`, `timezone` | Созданный бизнес и участие с ролью собственника |

Сервер проверяет попытку авторизации и адрес возврата. Токены провайдера не передаются frontend; сессия использует защищённую HttpOnly-cookie. Для изменяющих запросов предусматривается защита от CSRF.

### Точки, сотрудники и смены

| METHOD + URL | Назначение | Принимает | Возвращает |
|---|---|---|---|
| `GET /workplaces` | Список точек или одна точка | `id?`, `q?`, `cursor?`, `limit?` | Доступные точки, следующая страница, признак полноты загрузки |
| `POST /workplaces` | Создать точку | `name`, `timezone`; необязательно: `address`, `phone`, `description` | Созданная точка |
| `PATCH /workplaces/:id` | Изменить точку | Изменённые `name`, `address`, `phone`, `description` | Обновлённая точка |
| `GET /employees` | Справочник или один сотрудник | `id?`, `q?`, `workplace_id?`, `cursor?`, `limit?` | Сотрудники, связанные точки, статус подключения, сведения о полноте загрузки |
| `POST /employees` | Создать сотрудника | `full_name`, `workplace_ids`; необязательно: `email`, `phone`, `user_id` | Созданный сотрудник, его точки и статус подключения |
| `PATCH /employees/:id` | Изменить сотрудника / подключить аккаунт | Изменённые `full_name`, `email`, `phone`, `workplace_ids`, `user_id` | Обновлённый сотрудник |
| `GET /shifts` | Расписание или одна смена | `from`, `to`; необязательно: `workplace_id`, `employee_id`, `cursor`, `limit`; либо `id` одной смены | Смены с именами сотрудников, названиями точек, временем и длительностью |
| `POST /shifts` | Создать смену | `workplace_id`, `employee_id`, `starts_at`, `ends_at`; необязательно: `comment` | Созданная смена |
| `POST /shifts/bulk` | Сохранить сформированный график | `shifts` — массив из 1–31 смены с полями ручного создания | `created_count`, `shift_ids` |

Уточнения:

- `workplace_ids` — непустой массив уникальных идентификаторов точек.
- `user_id` — команда подключения аккаунта; в Employee сохраняется связь через `membership_id`.
- Статус подключения вычисляется: `not_linked` / `linked`.
- Контакты и связанные объекты возвращаются с учётом прав доступа.
- При фильтре `id` возвращается один доступный объект либо `404`; пагинация не нужна.
- Для получения одной смены по `id` параметры `from` и `to` не требуются.
- Часовой пояс существующей точки в первом спринте не меняется.

## 3. Подключение сотрудника в MVP

Предлагается временный способ без системы приглашений:

1. Сотрудник входит через Яндекс ID.
2. Копирует внутренний ID аккаунта из профиля.
3. Лично передаёт ID собственнику.
4. Собственник указывает `user_id` при создании или изменении сотрудника.
5. Backend связывает аккаунт с записью сотрудника.
6. Сотрудник обновляет доступ через `GET /api/session` и видит своё расписание.

Правила:

- Новая роль при подключении — `employee`.
- Существующая роль автоматически не меняется.
- Аккаунт, связанный с другим сотрудником этого бизнеса, подключить нельзя: `409`.
- Перепривязка к другому аккаунту в MVP не поддерживается.
- Контактный email не используется для автоматического подключения.
- Общий список чужих аккаунтов недоступен.

Систему приглашений и управление ролями через интерфейс переносим на следующие спринты. Для демонстрации администратора можно подготовить начальными данными.

**Временный способ подключения требует согласования.**

## 4. Генерация графика — Must have

- Frontend рассчитывает цикл: X рабочих дней / Y выходных.
- X и Y — целые числа от 1 до 31.
- Начало цикла сотрудника требует согласования с куратором. Текущий вариант — рабочая гипотеза.
- Один пакет относится к одному сотруднику и одной точке.
- Период — до 31 календарного дня.
- Длительность смены — 1–1440 минут.
- Frontend показывает предварительный список смен.
- После подтверждения отправляет массив в `POST /shifts/bulk`.
- Backend проверяет права, связи, время и все пересечения.
- Пакет сохраняется целиком одной транзакцией.
- При конфликте ничего не создаётся.
- Существующие смены не заменяются.
- Смена последнего дня не обрезается на границе периода.

## 5. Обязательные правила Backend

### Права

- Собственник управляет бизнесом, точками, сотрудниками и сменами.
- Администратор управляет расписанием доступных точек и читает необходимых для этого сотрудников.
- Сотрудник просматривает свои смены и назначенные точки.
- Права и принадлежность объектов бизнесу проверяются при каждом запросе.

### Время и смены

- Начало и окончание передаются с часовым смещением или `Z`.
- Время хранится в UTC; интерфейс использует часовой пояс точки.
- Конец смены позже начала.
- Предложенная длительность — 1–1440 минут.
- Обработка пересечений смен требует согласования с куратором. Текущий вариант — рабочая гипотеза.
- Проверка пересечений защищается от одновременных запросов.
- Календарь возвращает смены, пересекающие диапазон `[from, to)`, включая ночные.

### Запись данных

- Названия и имя сотрудника не могут быть пустыми.
- Сотрудник и его связи с точками сохраняются атомарно.

### Ошибки

| Код | Значение |
|---|---|
| `401` | Нет сессии |
| `403` | Нет прав |
| `404` | Объект недоступен |
| `409` | Конфликт смен, связи |
| `422` | Некорректные поля |

Формат ошибки:

- `error.code`
- `error.message`
- `error.field_errors`
- `request_id`

Ответы не содержат секретов и внутренних стеков ошибок.
