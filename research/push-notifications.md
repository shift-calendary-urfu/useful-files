# Пуш-уведомления: как работают, что нужно, нюансы

Исследование по задаче «Проанализировать инструменты для СМС, чата и отправки уведомлений» (#10).

## Коротко

- Для «Календаря смен» уведомления нужны, чтобы сообщать сотруднику: «тебе назначили смену» и «смена начинается через 2 часа».
- Пуши **бесплатны**, но работают через сервисы Google (Android, FCM) и Apple (iOS, APNs). Это значит полная зависимость от этих компаний.
- Если у нас **веб-приложение**, а не мобильное, подойдёт Web Push. Для быстрого старта можно взять Telegram-бота или email.
- Самая интересная часть для нашего проекта — не сама отправка, а **напоминания по расписанию** (см. «Нюансы»).

---

## Как работает пуш

На телефоне есть системная служба, которая держит постоянное соединение и принимает сообщения для всех приложений: у Android это **FCM** (Firebase Cloud Messaging, Google), у iPhone **APNs** (Apple). Наш сервер не соединяется с телефоном напрямую.

1. Приложение при запуске получает у платформы **токен устройства** (по сути, адрес конкретной установки).
2. Приложение отправляет токен на наш backend (например, `POST /api/devices`), мы связываем его с пользователем.
3. Когда нужно уведомить, backend вызывает API FCM/APNs, указав токен и текст.
4. Платформа доставляет сообщение на телефон, система показывает уведомление.

В вебе то же самое делает **Web Push** (протокол VAPID): браузер выдаёт подписку, сервер шлёт на неё сообщения.

## Что для этого нужно

| Платформа | Что требуется |
|---|---|
| Android (Google Play) | Проект в Firebase, ключ сервисного аккаунта для backend, клиентский SDK |
| iOS | Платная подписка Apple Developer, ключ APNs (часто подключают через FCM), настройка Push Notifications в Xcode |
| Android без сервисов Google (часть устройств в РФ, Huawei) | **RuStore Push SDK**, для Huawei дополнительно HMS Push |
| Веб | Service Worker на клиенте, VAPID-ключи на сервере |
| Backend | Хранилище токенов, очередь или планировщик задач (APScheduler, arq, Celery), клиентская библиотека (`firebase-admin` и др.) |

## Готовые решения

- **Firebase Cloud Messaging (FCM)** — бесплатный, основной вариант для Android, умеет доставлять и на iOS через APNs.
- **RuStore Push** — российский сервис для Android. Его SDK умеет работать совместно с FCM и HMS.
- **OneSignal и подобные платформы** — готовая панель, сегментация и аналитика поверх FCM/APNs. Удобно для рассылок, но данные пользователей уходят третьей стороне.
- **Telegram-бот** — бесплатно и просто: сотрудник один раз нажимает «Старт» у бота, backend шлёт сообщения по `chat_id`. Для учебного проекта часто самый быстрый путь.
- **Email** — запасной вариант без доп. настроек на клиенте.
- **Centrifugo PRO** — если будем использовать Centrifugo для чата, у платной версии есть push API.

## Нюансы нашего проекта

1. **Напоминания по расписанию.** Недостаточно «отправить пуш сейчас», нужно отправить его за N минут до начала смены. Для этого:
   - в базе хранится, когда и кому отправить;
   - фоновый процесс раз в минуту выбирает уведомления, время которых пришло;
   - при изменении или удалении смены напоминание нужно пересчитать или отменить.
2. **Часовые пояса.** В спецификации у точки есть `timezone`, а время хранится в UTC. Напоминание считаем от `starts_at` в UTC, а в тексте «в 09:00» показываем время по поясу точки.
3. **Токены устаревают.** Токен неактивного устройства считается устаревшим примерно через месяц, на Android истекает через 270 дней. FCM возвращает ошибки `UNREGISTERED` (404) и `INVALID_ARGUMENT` (400): такие токены нужно удалять из базы. Также удаляем токен при выходе из аккаунта. У одного пользователя может быть несколько устройств, токены хранятся по устройствам.
4. **Зависимость от Google и Apple.** Пуши на Android привязаны к сервисам Google, на iOS к APNs. В РФ из-за «белых списков» интернета возможны сбои: публиковались сообщения (март 2026), что из-за этого уведомления мессенджера MAX не доходили в ряде регионов. Полностью блокировать Google в РФ на данный момент не планируют, но риск остаётся.
5. **RuStore не полная замена FCM.** Это обычное приложение, а не системная служба, поэтому у части пользователей уведомления приходят с задержкой, а для работы может потребоваться выдать разрешения. Разработчики на практике делают **многоуровневый фолбэк**: FCM для устройств с Google, RuStore для остальных, плюс запасной канал внутри приложения.
6. **Критичное нельзя отправлять только пушем.** Новую смену или отмену нужно показывать и в самом приложении (список смен).
7. **Согласие пользователя.** Пользователь может не дать разрешение на уведомления (на Android 13+ и iOS оно запрашивается явно) или отключить их в системе. Нужен экран с объяснением, зачем нужны пуши, и запрос в подходящий момент.
8. **Согласованность с чатом.** Если сотрудник онлайн в чате, пуш о новом сообщении не нужен. Для этого нужна общая информация «кто сейчас в сети».
9. **Персональные данные.** Содержимое пуша проходит через серверы Google/Apple. Конфиденциальный текст лучше не отправлять, а присылать «у вас новое сообщение».
10. **Не слать лишнего.** Пользователь должен иметь возможность выбрать, какие уведомления получать (категории, тихие часы).

## Рекомендация

1. Для MVP: **Telegram-бот или email**. Для них не нужны аккаунты Apple, ключи и мобильный клиент.
2. Если клиент мобильное приложение: **FCM**, а для Android без сервисов Google добавить RuStore.
3. Сразу сделать слой `NotificationService.send(user_id, title, body)`, а внутри подключать каналы. Тогда добавление нового канала не затронет остальной код.

## План

| Этап | Что делаем | Результат |
|---|---|---|
| 1 | Решить, какие уведомления нужны на MVP (новая смена, изменение смены, напоминание) и на какие платформы | Список событий и платформ |
| 2 | Завести доступы: проект Firebase, при необходимости аккаунт Apple Developer + ключ APNs, проект в RuStore Console | Ключи и доступы |
| 3 | Таблица `devices(id, user_id, platform, provider, token, app_version, last_seen, enabled)`, уникальность по токену | Хранилище токенов |
| 4 | API: `POST /api/devices` (регистрация и обновление), `DELETE /api/devices/:id` (выход) | Клиенты могут регистрироваться |
| 5 | Класс `NotificationService` и реализации под каналы (`fcm`, `rustore`, `webpush`, `telegram`) | Единая точка отправки |
| 6 | Планировщик напоминаний: раз в минуту выбирает наступившие уведомления; пересчёт при изменении смены | Напоминания о сменах |
| 7 | Повторные попытки при ошибках, удаление мёртвых токенов | Надёжная доставка |
| 8 | Настройки пользователя: какие уведомления получать, тихие часы | Контроль у пользователя |
| 9 | Метрики: отправлено, доставлено, открыто, доля «мёртвых» токенов | Наблюдаемость |
| 10 | Проверка на реальных устройствах (с Google и без) | Тест в боевых условиях |
