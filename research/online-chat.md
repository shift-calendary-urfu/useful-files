# Онлайн-чат на FastAPI: как работает, готовые репозитории, подводные камни

Исследование по задаче «Проанализировать инструменты для СМС, чата и отправки уведомлений» (#10).

## Коротко

- Чат на FastAPI делается через **WebSocket**. Само ядро маленькое (около 10 строк), всё остальное — пользователи, база, проверки, надёжность.
- Репозиторий [Yakvenalex/FastApiChat](https://github.com/Yakvenalex/FastApiChat) — хороший **учебный** пример, чтобы понять принцип. Для настоящего проекта он слишком простой.
- Для нас хватит схемы **FastAPI + PostgreSQL**. Redis нужен, когда сервер запускается в нескольких копиях.
- В спецификации чат вынесен на следующие спринты, поэтому сейчас важно выбрать подход и не усложнять.

---

## Как работает чат

Обычный запрос (HTTP) — это письмо: спросили, ответили, соединение закрылось. **WebSocket** — это телефонный звонок: линия остаётся открытой, и сервер может сам написать клиенту в любой момент.

Путь одного сообщения:

1. Анна и Борис открывают чат, у каждого открывается WebSocket-соединение к серверу.
2. Сервер запоминает, кто на линии (обычно для этого есть объект «менеджер подключений»).
3. Анна отправляет сообщение по своему соединению.
4. Сервер проверяет, что Анна состоит в этом чате, и **сохраняет сообщение в базу** (источник истины).
5. Сервер находит соединение Бориса и пересылает ему сообщение. Если Бориса нет в сети, он увидит сообщение в истории при следующем входе (и, если нужно, получит пуш).
6. Историю клиент загружает обычным запросом, по страницам (у нас уже есть пагинация по `cursor`).

Ядро на FastAPI выглядит примерно так:

```python
@app.websocket("/ws/{chat_id}")
async def chat(websocket: WebSocket, chat_id: str):
    await manager.connect(chat_id, websocket)       # записали «на линии»
    try:
        while True:
            text = await websocket.receive_text()   # ждём сообщение
            await save_message(chat_id, text)       # сохраняем в БД
            await manager.broadcast(chat_id, text)  # рассылаем участникам
    except WebSocketDisconnect:
        manager.disconnect(chat_id, websocket)
```

## Почему в репозиториях так много файлов

Большая часть файлов не про чат: настройки, подключение к базе, миграции, Docker, список зависимостей, фронтенд. Для понимания достаточно найти:

1. файл с `@app.websocket(...)`: это живая часть;
2. файл с моделями (`Message`, `User`): как выглядят данные;
3. место, где сообщение сохраняется, и место, где оно рассылается.

Остальное можно пока не читать.

**Готовые серверы вместо своего кода**

- [Centrifugo](https://centrifugal.dev/): отдельный самохостящийся сервер, который держит WebSocket-соединения, а бизнес-логика остаётся во FastAPI. Есть история сообщений в каналах (по умолчанию выключена) и онлайн-статус. Минус: ещё один сервис, часть функций (в том числе push API) только в платной PRO-версии.
- **python-socketio** (Socket.IO): готовая библиотека с комнатами и автоматическим переподключением. История и статусы всё равно пишутся самостоятельно.
- **Облачные сервисы** (Ably, Pusher, PubNub и т.п.): быстро, но платно, и данные уходят третьей стороне.

## Подводные камни и на что обращать внимание

| Тема | В чём проблема | Что делаем |
|---|---|---|
| **Вход пользователя** | Браузер не может отправлять свои заголовки при открытии WebSocket, а токен в адресе попадает в логи | У нас сессия в HttpOnly-cookie, она отправляется браузером автоматически, отдельный токен не нужен. Проверять заголовок `Origin`, чтобы чужой сайт не подключился от имени пользователя |
| **Права доступа** | Проверка только при подключении недостаточна | Проверять членство в бизнесе и чате при каждой отправке и подписке |
| **Несколько серверов** | Если приложение запущено в нескольких процессах, список подключений у каждого свой и сообщение не дойдёт до клиентов на другом | Общая «шина» между процессами: Redis Pub/Sub (или Redis Streams / NATS). Пока копия одна, не нужно |
| **Потеря сообщений** | Redis Pub/Sub ничего не хранит: кто был не на связи в момент публикации, тот сообщение не получит | Источник истины — база. У каждого сообщения порядковый номер в чате (`seq`). Клиент после переподключения запрашивает «всё после номера N» |
| **Дубли** | При повторной отправке одно сообщение может сохраниться дважды | Клиентский идентификатор сообщения (`client_msg_id`), сервер игнорирует повторы |
| **Порядок сообщений** | В сети всё приходит с разной задержкой | Порядок определяет `seq`, а не время прихода |
| **Зависшие соединения** | Мобильные клиенты пропадают без «прощания», сервер копит мёртвые соединения; прокси могут обрывать неактивные соединения за 30–60 секунд | Периодические ping/pong (heartbeat), таймауты, настройка nginx |
| **Истёкшая сессия** | Соединение живёт долго, а сессия уже недействительна | Закрывать соединение особым кодом, клиент заново входит и подключается |
| **Медленные клиенты** | Один «тормозящий» получатель задерживает рассылку | Ограниченная очередь на каждого клиента, при переполнении отключаем |
| **Переподключение** | После обрыва связи клиенты лавиной стучатся на сервер | Клиент переподключается с нарастающей паузой |
| **Безопасность содержимого** | XSS, спам, слишком большие сообщения, вложения с вирусами | Экранирование при выводе, лимиты частоты и размера, загрузка файлов через временные ссылки в хранилище, проверка типов |
| **Нагрузка** | Один асинхронный процесс удерживает порядка тысяч-десятков тысяч соединений (оценка из открытых источников) | Измерить на своём оборудовании (k6, Locust) |
| **Деплой** | При перезапуске сервера все соединения рвутся | Плавное завершение (graceful shutdown), автоматическое переподключение клиента |
| **Персональные данные** | Переписка — чувствительные данные | TLS, политика хранения и удаления сообщений |

## Рекомендуемая архитектура для старта

- **FastAPI** — обычное API (чаты, история, участники) и WebSocket-эндпоинт для живых событий.
- **PostgreSQL** — чаты, участники, сообщения (источник истины).
- **Redis** — Pub/Sub между процессами, статусы присутствия, счётчики лимитов (когда понадобится больше одной копии сервера).
- **Очередь задач** (arq/Celery) — пуши и фоновая работа.
- **S3-совместимое хранилище** — вложения (если нужны).
- **nginx** — прокси с правильными таймаутами для WebSocket.

## Минимальная модель данных для нас

- `chats(id, business_id, workplace_id?, type, created_at)` — чат бизнеса, точки или личный;
- `chat_members(chat_id, user_id, role, last_read_seq)` — участники и позиция прочтения (по ней считаются непрочитанные);
- `messages(id, chat_id, seq, sender_id, client_msg_id, body, created_at, edited_at, deleted_at)`, уникальность `(chat_id, seq)` и `(chat_id, client_msg_id)`.

## Рекомендация

1. Начать с простой версии: FastAPI + PostgreSQL + WebSocket + история с пагинацией.
2. Взять [sh1nkey/fastapi-chat](https://github.com/sh1nkey/fastapi-chat) как образец структуры (а не копировать целиком), а Yakvenalex как объяснение принципа.
3. Redis добавлять только при нескольких копиях сервера.
4. К Centrifugo возвращаться, если не хватит нагрузки или времени.

## План

| Этап | Что делаем | Результат |
|---|---|---|
| 0 | Запустить 2–3 примера локально, разобраться, как идёт сообщение; проверить лицензии | Решение: берём как образец, а не копируем |
| 1 | Модели и миграции, REST: создать чат, список чатов, история с пагинацией по `cursor` | Чат без realtime |
| 2 | WebSocket: подключение по сессии, подписка на чаты, проверка прав, отправка, подтверждение (ack), защита от дублей | Живые сообщения на одном сервере |
| 3 | Redis Pub/Sub для нескольких процессов, heartbeat, переподключение с догрузкой по `seq` | Масштабируемость и надёжность |
| 4 | Статусы прочтения, «печатает», онлайн-статус, непрочитанные | Привычное поведение мессенджера |
| 5 | Вложения через хранилище, лимиты, фильтрация | Файлы и картинки |
| 6 | Связка с уведомлениями: офлайн-получатель получает пуш (см. `push-notifications.md`) | Единый сценарий |
| 7 | Нагрузочное тестирование, мониторинг (число подключений, задержка, ошибки) | Готовность к запуску |
